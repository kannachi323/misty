# Misty App runtime

## Rendering contract

Misty uses three rendering paths:

1. Trusted features compiled into the host render directly in the host React tree. A fixed identity allowlist selects compiled modules; no catalog field can supply a module URL or promote downloaded JavaScript to host trust. These features inherit host authentication and remain subject to account and Space authorization on the server.
2. Installed web packages render in native child WebViews on desktop. They do not receive the host DOM, account credentials, API tokens, settings document, or general native commands.
3. Simple third-party widgets use a validated declarative document rendered by host components. Version 1 supports plain text, inputs, preview buttons, separators, and spacing. Version 2 may attach one of four fixed capability actions to a button. Installed native libraries are no longer loaded into Misty during discovery or panel execution.

The installed-package launcher uses `NativeAppView` and never creates an iframe. The Browser also uses a native child WebView and has no web-build iframe fallback; the web companion offers to open the address in the default browser. The Host CSP permits scripts only from the Host itself, so package and catalog script origins cannot load into the Host tree. HTML email display is a separate content-rendering concern and is not an App runtime.

The account App registry (`/apps` and `/me/apps`) remains the source of truth for Discover, installation, navigation, and review. Transfers belongs to Files at `/apps/files?view=transfers`; legacy Transfers links and saved tabs still migrate there.

## Compiled features

`trustedHostApps.ts` selects the ten shipped Apps by their exact catalog identity. `TrustedAppSurface` lazy-loads only source modules compiled into Misty. `TrustedAppRouteScope` translates public App links into the existing feature routes while retaining the outer workspace router and host providers. Back, subsection changes, cross-feature links, and cross-Space links are covered by regression tests.

Trusted feature installation no longer downloads a second copy of the feature or creates an app-runtime session. The official catalog advertises these features as `embedded` on supported platforms and contains no package URL, hosted document, checksum, or signature. Its release builders reject accidental official package generation. Previously installed packages can remain on disk for migration purposes; they are not executed for these features.

## Native package boundary

`src-tauri/src/platform/mini_app.rs` creates registered, top-level native WebViews. Each receives a nonpersistent browser store and its own temporary profile directory. Persistent SDK storage is separately namespaced by account and immutable App identity. Native storage persistence is intentionally not shared with the host or another App.

The package protocol identifies the caller using Tauri's native WebView label. Requests must address that same registration and remain inside its canonical package directory. Traversal, symlinks outside the package, foreign registrations, remote startup URLs, top-level navigation outside the registration, new windows, and direct downloads are denied. A restrictive response CSP confines document resources and ordinary fetch requests to local assets and the native IPC transport. Media/clipboard Permissions Policy is denied by default. On macOS, a per-App WKUIDelegate also denies direct capture, motion requests, and file-upload panels. It is installed on an empty WebView before package navigation; the trusted main view keeps its own delegate. Other platform adapters and OS consent flows still need platform validation.

Ordinary websites never render in the Host DOM. Browser tabs share a Browser-only profile on Windows and Linux and a named Browser-only WebKit data store on macOS 14+ and iOS 17+. This preserves website sign-ins across Browser tabs without sharing the Host renderer's website data. Older Apple releases use nonpersistent Browser-only stores because named persistent stores are unavailable there; sign-ins last at most for the process and may not carry across tabs. Browser views receive no Tauri plugin capability and the application command dispatcher denies every Host command from their labels.

On macOS, App preferences also disable PeerConnection/WebRTC, direct media devices, JavaScript clipboard access, and DOM paste before package navigation. The configuration checks each selector and reads back the disabled value; unsupported engines fail startup rather than silently losing the policy. The trusted Host retains its own preferences and supplies granted device operations through the SDK. These controls use [WebKit's private preference API](https://github.com/WebKit/WebKit/blob/main/Source/WebKit/UIProcess/API/Cocoa/WKPreferencesPrivate.h), so OS-version compatibility and distribution constraints must be resolved before release. Equivalent Windows/Linux enforcement is still pending. Third-party packages that require their own WebRTC connections are currently unsupported; a future scoped real-time capability must mediate those operations rather than re-enabling unrestricted constructors. This closes a specific connection path; it is not a claim that every engine networking feature has been audited.

Tauri's application command dispatcher accepts general host commands only from the compiled main and bot views. A content view may invoke only `mini_app_rpc`, which also requires a live native registration. Tauri plugin permissions are separately scoped to the main/bot views; the App view receives none of the host's clipboard, keystore, filesystem, opener, window, or event grants.

RPC correlation IDs are generated in Rust. Requests are delivered only to the main host view. Only that view can answer them, post public context, resize, or close App views. Requests and responses are bounded; pending requests are limited and expire. Native timeout events cancel the matching host request, dismiss its permission prompt, stop recording, and prevent late responses. Closing a view drops pending replies; session expiry also closes the native view and cancels pending host requests. React remounts the package instance when account, App, Space, or session grants change.

The JavaScript startup adapter supports the existing package and extension message formats within the top-level native document. `window.parent` is the App itself. This adapter is compatibility transport, not a security boundary; the native registration, command policy, plugin ACL, protocol containment, and capability dispatcher enforce the boundary.

## Capability migration status

The existing capability gateway provides namespaced local/synced storage, App-owned navigation, toast UI, and a private legacy official HTTP bridge using short-lived app tokens. Request payloads cannot choose another App identity. Compiled host features no longer need this legacy HTTP bridge.

The migration is **not complete**:

- Extend and validate the new device grant service across platforms and the remaining operations. Session grants now cover chosen text-file handles, chosen folders and read-only scan jobs, clipboard text, origin-limited network calls, and bounded host recording. Chunked binary reads and staged output copies are implemented. General directory operations, large-file I/O scheduling, and other device services remain to be implemented.
- Finish replacing the extension legacy command broker, including selected-path handling. Storage Report, Themes, Image Optimizer, Quick Convert, Backups, and yt-dlp now use explicit native capabilities and cannot fall back to their legacy commands. Backups is currently local-only; migrated process services require equivalent confinement on other platforms. Installed native-library execution has been retired; any remaining legacy command ownership checks do not provide the full new grant model.
- Expand declarative widgets only when another operation can be expressed as a fixed, reviewable Host action. Version 2 currently supports clipboard read/write, chosen UTF-8 text-file reading, and origin-scoped GET requests; it does not accept scripts, handlers, generic commands, paths, or arbitrary request options.
- Complete the operation audit against manifests, backend authorization, installation grants, and OS permissions. Planner calendar/integration mappings now have targeted contract coverage; real account workflows and media-device enumeration still need verification.
- Implement and test isolated native App adapters for iOS/Android. Untrusted packages currently show an explicit unsupported-platform state there and in ordinary web builds. Compiled host Apps still render directly on supported platforms.
- Validate revocation during pending work, native view/modal placement, real app workflows, and platform-specific capture/network enforcement. CSP and WebView separation alone are not a claim of OS process/network isolation.

## Package migration

The extension catalog release is version 0.4.0. The Store keeps the installed version separately from the catalog version, compares semantic versions conservatively, and offers **Update** when a newer artifact exists for the current platform. Disabled Apps can update without being enabled first. Downloads still require a published SHA-256 checksum. Before replacing an existing package, the native installer validates the staged manifest ID, expected version, supported WebView runtime, safe relative HTML entry, and optional metadata identity. A failed validation leaves the installed package in place.

The six migrated packages contain only web assets and declare exact runtime capabilities in the manifest, detail metadata, and catalog. Their release workflow no longer downloads, signs, or embeds extension-owned executables. Catalog artifacts are currently published only for macOS arm64 and x86-64, where the native WebView and restricted process controls have been exercised. Windows and Linux artifacts remain withheld until equivalent controls are implemented and validated. This is a catalog availability limit; compiled Host features retain their existing platform support.

## Data-only widget format

An installed extension can put `ui` on a panel in its `plugin.json`:

```json
{
  "id": "greeting",
  "name": "Greeting",
  "status": "installed",
  "panels": [{
    "id": "main",
    "title": "Greeting",
    "ui": {
      "version": 1,
      "elements": [
        {"kind": "input", "id": "name", "text": "Name"},
        {"kind": "text", "id": "greeting", "text": "Hello {{name}}"},
        {"kind": "button", "id": "preview", "text": "Preview"}
      ]
    }
  }]
}
```

The host validates version, node kinds, unique IDs, properties, input names, and size limits. Text substitutions are a single bounded pass and never evaluate expressions or HTML. Preview buttons submit the host-owned input values to the same data renderer. Version 2 buttons may declare only `clipboard.writeText`, `clipboard.readText`, `files.readText`, or `network.fetch`. Action values receive the same bounded, single-pass text substitution. File reading is a compound Host action that presents a native picker, reads at most 256 KB of UTF-8 text, then releases the handle. Network actions are GET-only and still require an exact HTTPS origin in the package manifest plus explicit approval; the existing public-address and response-size checks apply. Widgets cannot supply event handlers, scripts, native paths, generic commands, executables, headers, request bodies, or HTML.

Each declarative panel gets a headless native permission registration derived from its canonical package, account, and active Space. It has no WebView or script context. Its handles, grants, denials, pending prompts, and operations use the same instance-owned registry and revocation logic as isolated Apps, and are dropped when the panel closes or identity changes. The document is limited to 64 KB and 128 elements. Existing version 1 widgets remain valid. Extensions that require richer dynamic UI use the isolated native WebView and capability API.

## Device capability API

`@misty/sdk` now connects directly to the native `mistyHost` transport and announces readiness without a parent frame. It exposes `files.pick/readText/writeText`, `clipboard.readText/writeText`, `network.fetch`, `microphone.capture`, `camera.capture`, and `permissions.list/revoke`. The existing legacy extension command broker is not yet migrated to these operations.

A `mini-app.json` uses machine-readable `capabilities` and `networkOrigins`. Legacy extension `plugin.json` can declare these as `runtime_capabilities` and `runtime_network_origins`; descriptive prose in legacy `permissions` fields is never interpreted as a grant. The native loader derives installation identity from its package, reads declarations inside that package, and intersects declarations with server-issued scope limits when supplied by the host. A package cannot expand that limit.

The host-owned **App permissions** toolbar stays outside the native content rectangle. Device requests prompt in the host, other embedded views suspend while the prompt is open, and only the main host can record the decision. Grants last for the open instance. Denial or revocation blocks repeated prompts for that session; reopening starts with no grants. Revoking file access drops selected file handles. Closing the instance drops every grant.

File operations use opaque IDs and an open descriptor for each user-selected file. App-supplied paths are not accepted. Writing requires both a write grant and a file chosen for writing. Current text operations are bounded to 256 KB. Chosen-folder scan access is implemented; general directory operations and large binary streaming remain future migration work. Network grants are per declared HTTPS origin; requests omit inherited cookies/proxies, reject local/private addresses, pin DNS results, disable redirects, and bound response size. Revocation or close cancels a pending network lease. The broker does not claim OS-wide network isolation from CSP alone.

Host recording has a visible cancellation dialog, duration/size bounds, and stops tracks on cancellation, revocation, or app closure. Camera capture does not imply microphone permission. No recording bytes are returned after revocation. These behaviors have unit coverage with fake media devices; real hardware/OS-consent workflows still need validation. Native debug builds additionally exercise the installed WKUIDelegate callback to verify direct capture returns Deny without opening a real device.

## Planner loading audit

Agenda results no longer wait for account and integration management lookups. Published calendar sources load independently, while integration/account management requests are limited to users who can manage integrations. Changing account/App/Space remounts the compiled feature boundary to discard previous feature state.

The legacy app-token gateway now explicitly enumerates calendar and Space integration routes. Calendar operations require `calendar.read/write`, integration operations require `connections.read/write`, calendar synchronization also requires `tasks.write`, and browsing connected Google calendars requires both read capabilities. Unknown routes and other Spaces remain denied. The existing handler/database membership and management checks still apply. Planner's catalog permission version is 3 and includes the audited scopes; existing installations must review the added permissions. The local package and generated server catalog have been synchronized, but this is not evidence of a deployed backend update.

App record reads and writes now require `storage.read/write` on the backend as well as the host gateway. Installation grant changes retire tokens with different grants; token issuance locks the installation row to serialize against those changes. Token lookup additionally checks that issued scopes are still contained in current installation grants. Regranting a permission does not revive a retired token. The host API forwards cancellation and never forwards the app token or cookies to signed resource downloads.

## Chosen folders and Storage Report

`files.pickDirectory` opens the native folder picker after a `files.read` grant. It returns a random handle and display name, never an absolute host path. Native state retains an open directory using [cap-std’s directory capability](https://docs.rs/cap-std/4.0.3/cap_std/fs/struct.Dir.html). Scan traversal resolves relative to that handle, including after the original pathname is replaced. Symbolic links and special files are skipped. Results contain relative paths and size metadata; the API does not read file contents.

`files.scanStart`, `scanStatus`, `scanCancel`, and `scanClose` manage jobs inside one native registration. Knowing another instance’s job ID grants no access. Revoking file access clears folders and jobs; closing the instance does the same. Workers check cancellation between filesystem operations and discard late results. An operating-system filesystem call already in progress may finish before cancellation is observed. Four scans may run across the host, with sixteen retained jobs and thirty-two folder handles per instance. Scans bound their duration, entry count, traversal depth, pending folders, and report size. A partial scan is labelled in the UI.

Storage Report now uses these SDK methods directly, asks the user to choose its folder, and shows explicit native permission errors. It no longer receives Files selection paths or submits `storage_report.start` through the legacy broker. Its package declares `files.read`; its launcher no longer requires an existing Files selection. The other five catalog Apps have also moved to explicit capability APIs, and the broker rejects their retired commands.

## Themes and appearance capabilities

Themes now connects through the native SDK. `appearance.snapshot` returns only the public theme palette after checking that the native instance still exists; it does not require access to account or device data. `appearance.preview`, `appearance.preset`, `appearance.apply`, and `appearance.revert` require a declared `appearance.write` capability and explicit session approval. The Host checks the native grant again immediately before applying the validated preset or color-token operation. No arbitrary setting key, CSS, file path, or generic command is accepted.

Previews are owned by the native instance. Revocation, expiry, or closure removes that instance's unsaved preview; closing an older instance cannot remove a newer instance's preview. Saved settings remain saved after access is revoked. Themes receives no Files selection paths and its old command interface is rejected. The text-color editor now uses the Host's `text` and `textMuted` keys, fixing previously ignored edits. Both its catalog and package declare `appearance.write`.

Regression checks cover approval before changing settings, a second grant check, revocation cleanup, cross-instance preview ownership, and persistence after preview cleanup. Native policy tests cover declaration, server-scope intersection, grant, revoke, and denial of unknown appearance operations. The native workflow example accepts `--themes` to load the actual rebuilt Themes bundle. Interactive Themes validation remains pending: the Mac was locked when that check was attempted. Storage Report's earlier interactive results above remain separate evidence.


## Binary files and Image Optimizer

The SDK now provides `files.pickMany`, `files.readBytes`, `files.createCopy`, `files.appendCopy`, `files.commitCopy`, `files.discardCopy`, and `files.release`. Picking files requires `files.read`; reads use the retained descriptor and transfer at most 64 KB per call. Up to 64 files may be selected at once, with 128 retained handles per instance so an app can replace its current selection. `files.pickDirectory({write:true})` requires `files.write` and records that the chosen folder is writable. A folder chosen for reading cannot be upgraded just by subsequently granting write permission.

Creating a copy requires that writable folder handle and a simple filename. App paths, separators, control characters, and reserved device names are rejected. Up to four unfinished copies per instance are staged in host temporary files, bounded to 256 MB each. Commit creates a new file exclusively in the retained directory and adds a numeric suffix for collisions. Originals and existing symlinks are never overwritten. Revocation or closure drops drafts; releasing an output folder also discards its drafts. Discarding a draft never deletes a committed file.

Commit currently serializes with permission changes while it copies the staged file into the chosen directory. Once that save begins, revocation takes effect for subsequent operations; it does not roll back completed writes. A filesystem failure during commit can leave a partial copy and returns that fact and its display name. It deliberately does not unlink by pathname after an error, because another process could replace that pathname. Filesystem I/O that blocks inside the OS remains a performance limitation to address before broad platform signoff.

Image Optimizer uses this API without host paths or an external executable. Its image decoder/encoder runs inside the isolated WebView. It supports batches, quality, dimension limits, progress, cancellation, and per-file outcomes. Inputs are limited to 64 MB and decoded dimensions to 32 million pixels. When a smaller encoding is unavailable without resizing, it copies the original bytes; when an encoder falls back to PNG during resizing, the output gets the correct PNG extension. App cancellation discards unfinished output and keeps completed copies. The catalog and package declare only `files.read/write`, no longer require Files selection or FFmpeg, and the legacy command broker rejects Image Optimizer requests. The previous Show Output command is not exposed: the UI reports the chosen destination and saved filenames; a safe native reveal operation is still needed for full workflow parity.

Rust regression tests cover descriptor reads after pathname replacement, size/offset bounds, read-only folders, invalid names, foreign handles, collision and symlink safety, draft disposal, and revocation. App tests cover chunking, cancellation before commit, revoked writes, input bounds, and fallback filename extensions. The interactive native fixture accepts `--optimizer` and creates an example image and output folder. Real WebKit codec and picker validation is pending while the Mac is locked; unit tests inject an encoder and do not prove that native workflow.


## Quick Convert and restricted media jobs

Quick Convert now uses chosen file and writable-folder handles and declares `files.read`, `files.write`, and `media.convert`. Native registration owns each conversion ID. `media.convertStart` accepts only handles, a simple output filename, an enumerated format, and quality. It accepts no executable path, environment, shell, command line, filter graph, network URL, or host path. The native service separately checks the file grants. Status, cancellation, collection, and closure require the media grant and owning registration. Collection creates a staged copy; saving uses the same exclusive new-file commit as Image Optimizer. Closing, cancelling, revoking relevant grants, or releasing a referenced file/folder discards pending conversion work. Earlier committed copies stay saved.

On macOS the worker resolves FFmpeg from the Host environment/system installation and rejects an executable inside installed App packages. The job copies the open input descriptor into a private temporary directory and launches the fixed conversion under `sandbox-exec` with a deny-by-default profile. It permits reads of its job directory, the selected executable, system libraries, and Homebrew dynamic libraries; it permits writes only within the job directory. Filesystem metadata, root-directory enumeration, and sysctl reads are allowed for loader/runtime initialization. User-file contents, network access, and execution of other programs are denied. The environment is replaced with fixed PATH/LANG and temporary HOME/TMPDIR; no Host environment credentials are inherited. The profile specifically avoids allowing all of `/System`, which would include the writable Data volume.

[FFmpeg's protocol allowlist](https://ffmpeg.org/ffmpeg-protocols.html) adds an input restriction to local file/pipe protocols; the OS tests deliberately omit this option to verify that network and ungranted-file denial comes from the process policy itself. A separately installed `/opt/homebrew/bin/cwebp` or `/usr/local/bin/cwebp` provides WebP encoding when present, in a second restricted process; this supports the compact Homebrew FFmpeg build that omits WebP. App packages cannot select either executable or its arguments. Both processes share only their temporary job folder.

Two jobs may run across the Host, with four retained jobs per App instance. Inputs are bounded to 1 GB, outputs to 256 MB, and job wall time to five minutes. Child CPU/file-size/file-descriptor limits, FFmpeg allocation/pixel limits, and fixed thread options apply. Cancellation kills and reaps the child's process group, and no result is published after cancellation. macOS rejected finite DATA/AS/RSS limits in this environment; this implementation does not claim a hard OS memory quota. Codec-dependent memory use and cancellation during an OS-blocked input read remain limits to address. The deny-by-default process adapter currently exists only on macOS; other platforms report unavailable without executing a less-restricted fallback. Packaging a managed Host toolchain and implementing other-platform process adapters remain release work.

Legacy native Quick Convert and Themes panel actions were removed. Old builtin shortcuts open the App; old native-only panels require an updated package. The web plugin broker rejects the migrated Quick Convert transport just as it rejects Storage Report, Themes, and Image Optimizer. This removes the separate path-based execution route instead of relying only on the new UI. The previous automatic job recovery across closed app instances is deliberately replaced by cancellation on close. A safe output-reveal operation and interactive native-app validation are still required for full workflow parity.

Tests cover actual restricted audio conversion, ungranted reads/writes, blocked loopback networking, a replaced environment, denied child execution, process cleanup, instance-owned collection, revocation before save, and client cancellation. The real format matrix passed for PNG, JPEG, WebP, AVIF, MP3, WAV, FLAC, M4A, MP4, MOV, WebM, and GIF using this Mac’s FFmpeg 9.0.1 and cwebp 1.6.0. It exposed and fixed a short-input GIF frame-rounding failure as well as the absent FFmpeg WebP encoder. Native picker/UI validation remains separate from process-level tests.

The interactive native workflow fixture also accepts `--convert` to load the actual rebuilt Quick Convert package and supplies a generated image plus an output folder. The Mac remained locked at the latest attempt, so process and unit results are not reported as interactive picker/App validation.

## Public media downloads

The rebuilt yt-dlp App uses `media.download` plus a writable folder handle. It can request review or download of a public HTTPS URL, choose one of four fixed output formats, and opt into a playlist capped at 100 entries. It cannot supply a command, executable, arguments, environment, output path, proxy, cookie source, or arbitrary destination. The Host returns bounded title/uploader/duration/count fields during review and display names plus sizes after saving; raw extractor metadata, resolved URLs, private paths, and worker logs are withheld. The app package no longer contains or declares executable tools, selected Host paths, shell access, or the legacy job broker.

On macOS the Host selects managed yt-dlp, FFmpeg, and FFprobe installations and launches them under a deny-by-default process policy. The worker can read only those managed runtimes, system loader files, the system certificate bundle, and its private job directory; it can write only inside that job directory and execute only the fixed Python runtime and media tools. Its environment is replaced with six fixed variables. CPU, individual file, descriptor, and wall-time limits apply. Other platforms return unavailable until they have an equivalent process adapter.

The worker has no general outbound socket permission. It receives an authenticated loopback proxy URL, and the sandbox permits TCP only to that exact port. The Host proxy resolves each requested destination once, connects to the selected address directly, and rejects loopback, private, link-local, carrier-grade NAT, documentation, benchmark, multicast, and reserved IPv4/IPv6 ranges. It supports only authenticated HTTP requests on port 80 and HTTPS tunnels on port 443, limits concurrent connections to 16, idle connections to 90 seconds, total traffic to 10 GiB, and shuts down with cancellation. The App's initial URL must be HTTPS without credentials or a custom port. This prevents the downloader from being used as a direct local-network client while retaining extractor flexibility across public media hosts.

Completed files remain in a private native directory until the worker exits successfully. The Host opens only bounded, regular files listed by the fixed completion log, rejects symlinks and paths outside that directory, then copies each file in bounded chunks into a random exclusive temporary file under the retained destination handle. A hard link publishes a new collision-safe name, so existing files and symlinks are never overwritten and partial downloads are not published. Revoking `media.download` or `files.write`, releasing the destination, closing the job, or closing the App cancels the process, proxy, and save work. A multi-file publish can save earlier completed items before a later filesystem error; the failure message reports that count.

Tests cover URL and private-address rejection, proxy authentication, foreign endpoint denial, output redaction, exclusive collision-safe saves, revocation cancellation, loading the real Homebrew Python-based yt-dlp inside the sandbox, and denial of a direct loopback bypass. An opt-in network integration reviewed and downloaded a public five-second MP4 through the Host proxy. Native picker/UI validation and broader extractor compatibility remain pending.

## Backups: grant-owned local repositories and jobs

The rebuilt Backups UI uses the native SDK and no longer receives selected Host paths or sends commands through the legacy extension broker. `backups.manage`, `files.read`, and `files.write` are declared in both package metadata documents. The Host owns repository and job handles, presents every folder picker, retains folder descriptors, applies revocation, and returns only display names, bounded progress state, snapshot IDs/times, and restore results. Repositories are bound to the Host-derived account/App/Space namespace and a random vault record; neither the vault key, password, repository path, source path, private endpoint, nor worker command line is disclosed to the App.

This migration currently supports local repositories on macOS. Cloud-provider grants, migration of repositories created by the legacy Backups package, and equivalent confined workers on other platforms remain before full Backups parity.

The new native repository service implements the relevant [Restic REST backend operations](https://github.com/restic/restic/blob/master/doc/REST_backend.rst) against an already-open `cap_std::fs::Dir`. Restic receives a private loopback endpoint with a fresh per-server authentication token. The App receives neither the token nor a host filesystem path. Source/repository folder authority is not passed to Restic as an ambient pathname. The service resolves fixed repository object types and hexadecimal object IDs, uses the standard local `data/<prefix>/<id>` layout, and rejects traversal and symlink targets. A retained root continues to identify the original directory after its path is replaced.

Uploads publish an immutable object through an exclusive temporary file and a hard link; an existing object's identical retry is accepted, but different content and symlink replacements cannot overwrite it. Only lock objects can be deleted. Full repository deletion, prune, and forgetting snapshots are not exposed. Reads support explicit byte ranges, and listing returns REST v2 metadata. Per-server processing is limited to two requests, each blob to 64 MiB, enumeration to 250,000 entries, and request-body reception to 30 seconds. Repositories using larger pack files will need an explicitly supported streaming path before compatibility can be claimed for them. The service currently buffers bounded blobs in memory. Revocation waits for active bounded filesystem operations and then denies queued work; a stalled filesystem can delay that acknowledgement, so callers must keep this off the UI thread.

The macOS worker has a deny-by-default process policy. It can execute only the Host-selected executable, read system loader files and its private working directory, write only its working directory, and connect only to the native repository's localhost TCP port. It has no inherited environment, proxy settings, cloud credentials, browser cookies, source paths, or repository paths. A job-specific repository password is supplied by the native owner. CPU/open-file/core-dump limits and `GOMAXPROCS=2` are set. The two-worker scheduler holds a slot for the filesystem streaming thread even after cancellation until that thread actually exits. Hard memory and disk quotas remain unfinished. Other platforms return unsupported until equivalent confinement exists.

The integration test uses temporary fixtures and a real Host-installed Restic to initialize a repository, back up streamed input, list snapshots, verify encrypted data, and restore the original bytes under the process policy. A separate standard local Restic check verifies compatibility of the generated repository layout. Process checks use a working localhost port as a positive control and deny another port, ungranted file reads/writes, and child execution; the worker environment contains only the six explicitly supplied variables. Separate repository checks cover unauthorized requests, browser Origin rejection, range handling, immutable writes, path/symlink containment, retained-folder identity, and revocation during a partially received upload before any repository file is published. Real Backups picker/UI validation, legacy repository recovery, and cloud backups are still required before completion.

### Folder streaming and native restore

The in-progress Backups worker now streams a TAR archive from retained source-folder handles into restricted Restic and streams `restic dump` back into a native extractor. No whole-folder temporary copy or ambient source/restore path is passed to Restic. Source names remain visible inside the archive; duplicate chosen-folder names receive distinct suffixes. The archive preserves regular-file contents, hard links, symlink targets, long/Unicode names, regular-file and directory permission bits, modification timestamps, and bounded macOS extended attributes. Binary attributes use length-parsed PAX records, including embedded NUL/newline bytes. File changes detected during streaming fail the backup. This is a new streamed snapshot format (`Misty Backup.tar`); restoring older snapshots that contain ordinary Restic trees still requires a separate migration path.

Restore uses raw TAR iteration so oversized GNU/PAX headers cannot trigger unbounded parser allocation. It accepts only supported entries and metadata, rejects escaping/duplicate paths, does not follow symlinks during directory traversal, and creates files exclusively. Hard links must refer to an already-restored regular file. Device/special entries, malformed metadata, truncated bodies, missing end markers, and unexpected trailing content fail. Every restore gets a new collision-safe `Misty Restore` folder. Partial contents may remain there after failure, while existing user files are never overwritten or blindly deleted by pathname.

Current streaming limits are 64 source folders, two million content entries, depth 128, 64 TiB of file data, 128 MiB of indexed path bytes, 32 MiB per metadata record, 16 MiB of extended attributes per entry, and 64 MiB of deferred directory metadata. Individual read/write calls are bounded to 64 KiB. ACLs, ownership, filesystem flags, symlink timestamps/attributes, sparse-file efficiency, other-platform metadata adapters, and fuller metadata compatibility remain to be implemented/validated before full Backups parity can be claimed. Unsupported special source files currently fail the operation rather than being silently omitted.

The worker retains its input pipe until streaming succeeds, kills the process group before closing a failed input stream, and checks cancellation plus a 24-hour deadline. Cancellation errors are deliberately non-retryable by Rust's I/O helpers. The repository buffers the final encrypted Restic snapshot record in a native transaction: publication requires both validated archive completion and successful Restic exit. A failed stream or process resets the transaction, and App requests cannot open or finalize it. Cancellation kills and reaps Restic and unblocks its pipes, but a native thread stalled inside a filesystem operation may finish later while retaining its scheduler slot. Revoking file or backup access, closing the repository, closing the job, or closing the App cancels the owned work and drops its handles. Per-job stale-lock recovery remains unfinished.

Tests exercise metadata and link round trips, source path replacement, duplicate source names, traversal and symlink write denial, existing-file preservation, oversized metadata, truncated archives, and streaming cancellation. Process tests cover cancellation/reaping and killing before failed-input EOF. A real restricted Restic integration backs up a chosen folder, restores its original bytes through the extractor, and verifies that a failed source stream creates no additional snapshot. Capability tests cover result redaction, collision-safe restore destinations, and revocation cancellation. The SDK and rebuilt UI compile against the same methods, but the real native picker workflow remains to be exercised interactively.
