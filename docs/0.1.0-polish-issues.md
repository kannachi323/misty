# Misty 0.1.0 Polish Issues

This file is a backlog of issue-ready polish items for the `0.1.0` release.
The goal is not new platform scope. The goal is to make the current app feel
coherent, predictable, and releaseable.

## 1. Proxy Health And Restart UX

**Title:** Make proxy health and restart status explicit in the client

**Problem**
The client can end up talking to a stale or dead proxy process, and the UI
does not clearly distinguish between:
- proxy not reachable
- proxy reachable but missing routes
- proxy reachable but missing dependencies like `rclone`

**Expected outcome**
- Services and Settings show a clear proxy status section.
- Restart actions surface progress and success/failure details.
- Errors include the actual failing URL or HTTP response summary.

**Acceptance criteria**
- Add a visible proxy status indicator with `running / unreachable / restarting`.
- Show the configured proxy path and port.
- When restart fails, show a concrete error instead of a generic message.
- After restart, automatically re-run proxy health and remote health checks.

## 2. Rclone Setup Flow

**Title:** Polish external `rclone` setup and first-run guidance

**Problem**
The current `rclone` flow is functional but still feels internal. Users need a
clearer explanation of what Misty expects and what it will manage for them.

**Expected outcome**
- Users understand how cloud support works without reading logs.
- Misty can guide users from “missing rclone” to “ready”.

**Acceptance criteria**
- Services shows a short explanation of external `rclone` usage.
- Health UI shows:
  - resolved binary path
  - managed symlink path
  - config path
- Missing `rclone` state includes actionable guidance.
- Successful detection confirms that the managed symlink was created.

## 3. Services Panel Layout And Messaging

**Title:** Tighten Services panel hierarchy and action layout

**Problem**
The Services screen is usable but still reads as a developer tool in a few
places. Important actions and status areas compete visually.

**Expected outcome**
- The Services screen feels stable and intentional at common desktop sizes.
- Action order and health information are easier to scan.

**Acceptance criteria**
- Keep `Add Service`, `Check`, and `Restart Proxy` visible at narrow widths.
- Ensure health panels do not clip or push controls off-screen.
- Reduce redundant or overly technical copy.
- Improve spacing between:
  - health block
  - search/action row
  - connected services grid

## 4. File Explorer Empty, Loading, And Error States

**Title:** Normalize explorer empty/loading/error states

**Problem**
The file explorer works, but the surface still feels abrupt when switching
between empty folders, remote loading, missing proxy, and failed operations.

**Expected outcome**
- Explorer states feel deliberate rather than incidental.
- The user can tell whether the app is waiting, empty, or broken.

**Acceptance criteria**
- Add consistent loading indicators for remote folder fetches.
- Differentiate “empty folder” from “failed to load folder”.
- Show a recovery action for proxy-related failures where possible.
- Prevent stale selection or stale breadcrumbs after failed navigation.

## 5. Drag And Drop Navigation Feedback

**Title:** Refine drag navigation feedback across folders and breadcrumbs

**Problem**
The current drag navigation is better than before, but it still needs a
finishing pass so the interaction feels obvious and stable.

**Expected outcome**
- Drag hover feedback is consistent across:
  - folder items
  - breadcrumbs
  - back/forward navigation

**Acceptance criteria**
- Keep the open-folder icon behavior for folder hover targets.
- Use one visual language for breadcrumb and history hover feedback.
- Make drag-navigation transitions feel intentional rather than abrupt.
- Verify that background drop targets never steal folder navigation focus.

## 6. Undo/Redo UX For File Operations

**Title:** Surface undo/redo support clearly in the file explorer

**Problem**
Undo/redo exists for some operations now, but the user has little visibility
into what is undoable, what failed, or why an action cannot be replayed.

**Expected outcome**
- File operation history feels trustworthy.
- Keyboard shortcuts and menu actions behave consistently.

**Acceptance criteria**
- Show disabled states for undo/redo when unavailable.
- Add short user-facing feedback after undo/redo actions.
- Distinguish unsupported operations from failed operations.
- Verify shortcut consistency on Windows, macOS, and Linux conventions.

## 7. Boot Loader And Startup Messaging

**Title:** Make startup and boot loader transitions feel production-ready

**Problem**
Boot flow logic is functional, but its messaging and transitions still feel
debug-oriented in edge cases.

**Expected outcome**
- Startup states feel calm and intentional.
- Failure states point the user toward recovery instead of logs alone.

**Acceptance criteria**
- Replace vague startup failure text with actionable status.
- Clarify when Misty is:
  - starting proxy
  - waiting for proxy
  - switching to auth
- Reduce repeated startup attempts that spam logs.
- Keep startup behavior consistent between debug and packaged builds.

## 8. Settings And Diagnostics Surface

**Title:** Add a small diagnostics section for local runtime dependencies

**Problem**
Important runtime facts are spread across logs, Services, and implicit config.
There is no single place to inspect local app health.

**Expected outcome**
- Users can inspect local runtime setup without opening terminal logs.

**Acceptance criteria**
- Add a diagnostics section showing:
  - proxy path
  - proxy URL/port
  - `rclone` health
  - `restic` health
- Include copyable paths for local troubleshooting.
- Keep it read-only for `0.1.0`; no full config editor required.

## 9. Notification And Feedback Consistency

**Title:** Standardize success, warning, and error feedback across panels

**Problem**
The app currently mixes inline text, silent success, and generic failure
messages. That inconsistency makes the app feel unfinished.

**Expected outcome**
- Similar actions produce similar feedback patterns everywhere.

**Acceptance criteria**
- Define one pattern for transient success messages.
- Define one pattern for blocking errors.
- Avoid raw backend phrasing when a user-friendly message is possible.
- Keep detailed backend text available where it adds troubleshooting value.

## 10. Log Hygiene Before Release

**Title:** Reduce noisy startup/runtime logs and make release logs readable

**Problem**
Logs still contain repeated startup attempts and low-signal runtime noise,
which makes real failures harder to isolate.

**Expected outcome**
- Release logs are readable and focused on meaningful events.

**Acceptance criteria**
- Remove or demote repeated startup spam.
- Ensure dependency health logs are one-time and high signal.
- Keep explicit logs for:
  - proxy launch
  - proxy restart
  - missing `rclone`
  - missing `restic`
- Avoid panic-style output for recoverable conditions.

## 11. Release Checklist For Packaged Builds

**Title:** Create a final 0.1.0 release checklist for packaged app validation

**Problem**
A lot of current work has been validated in dev builds, but `0.1.0` needs a
repeatable last-mile checklist for packaged binaries.

**Expected outcome**
- Release validation is explicit and repeatable.

**Acceptance criteria**
- Verify packaged client launches proxy correctly.
- Verify `Restart Proxy` works in packaged builds.
- Verify `rclone` detection works when app is launched from GUI.
- Verify Services, Files, and Vault all behave without dev-only assumptions.
- Verify app copy, spacing, and status states on a clean user account.

## 12. Final Pre-0.1.0 UI Sweep

**Title:** Run a final consistency sweep across typography, spacing, and copy

**Problem**
The app has several individually decent screens, but the product still needs a
final pass to feel like one application.

**Expected outcome**
- Fewer rough edges.
- More consistent visual rhythm and copy tone.

**Acceptance criteria**
- Normalize section heading sizes across core panels.
- Normalize button heights and spacing in major workflows.
- Remove obviously internal/dev wording from user-facing text.
- Check for clipped controls, off-screen buttons, and inconsistent padding.

## 13. General Settings Information Architecture

**Title:** Expand General settings into clear, user-facing subsections

**Problem**
The current General settings surface is too thin for a file manager and does
not yet explain how Misty behaves at startup, how updates work, where local
runtime state lives, or which default file-handling behaviors the app will
use. That makes Settings feel unfinished even when the underlying behavior
already exists or is easy to expose.

**Expected outcome**
- General settings feels like a complete home for app-level preferences.
- Users can understand startup behavior, update behavior, and local runtime
  setup without leaving the app.
- File-manager defaults live in one predictable place instead of being spread
  across future panels.

**Acceptance criteria**
- Keep the existing `App` section, but reorganize General into:
  - `Startup`
  - `Updates`
  - `Behavior`
  - `System`
  - `Defaults`
- Each subsection should use the same row layout and tone as the rest of the
  Settings screen.
- Favor short, concrete labels over internal or implementation-heavy wording.
- Keep advanced troubleshooting detail visible but read-only in General.

### Startup

**Purpose**
Define what Misty should do when the app launches and when a user returns to
the app after closing it.

**Rows to include**
- `Default landing view`
  - Choose the first screen shown after launch, such as `Files`, `Services`,
    or `Activity`.
- `Reopen last session`
  - Restore the last active location, sidebar state, and recent context when
    the user relaunches Misty.
- `Launch on login`
  - Start Misty automatically when the user signs into their computer.

**Notes**
- `Default landing view` and `Reopen last session` should have clear
  precedence so the resulting behavior is predictable.
- If session restore is unavailable, the UI should explain that Misty will
  fall back to the default landing view.

### Updates

**Purpose**
Explain how the installed app receives updates and give the user confidence
that Misty is current.

**Rows to include**
- `Release channel`
  - Show the current track, such as `Stable`, and reserve room for future
    channels if needed.
- `Auto-update`
  - Let the user choose whether Misty downloads and applies updates
    automatically.
- `Check for updates`
  - Trigger an explicit update check.
- `Last checked`
  - Show when Misty last looked for updates.

**Notes**
- `Check for updates` should report one of:
  - already up to date
  - update available
  - update check failed
- If auto-update is disabled, `Last checked` still matters and should remain
  visible.

### Behavior

**Purpose**
Capture app-wide interaction defaults that shape how file operations feel day
to day.

**Rows to include**
- `Confirm before destructive actions`
  - Control confirmation prompts for delete, empty trash, clear recent items,
    and similar irreversible actions.
- `Default file action`
  - Define what a primary interaction should do, such as open, preview, or
    reveal details.
- `Open links externally`
  - Decide whether external links open in the system browser instead of being
    handled inside Misty.

**Notes**
- This section should reflect Misty's identity as a file manager, not a
  generic app shell.
- If destructive confirmations are split later, General can start with one
  umbrella toggle and move finer controls into Advanced only if needed.

### System

**Purpose**
Give users a compact, trustworthy summary of the local runtime environment
that Misty depends on.

**Rows to include**
- `Proxy status`
  - Show whether the local proxy is running, unreachable, or restarting.
- `App version`
  - Show the installed version clearly.
- `Build info`
  - Show useful read-only build metadata for support and debugging.
- `Config path`
  - Show the local settings/config directory.
- `Data path`
  - Show where local app data is stored.

**Notes**
- This section should complement, not replace, the dedicated diagnostics work
  already planned elsewhere in this doc.
- Paths should be copyable.
- Proxy health language should match the wording used in Services and other
  diagnostics surfaces.

### Defaults

**Purpose**
Define file-manager defaults that influence where Misty starts working and how
common transfers behave before the user changes anything in context.

**Rows to include**
- `Preferred workspace root`
  - Choose the default root location or starting workspace for file browsing.
- `Mount path`
  - Show or edit the default mount location used by Misty.
- `Default transfer behavior`
  - Set sensible defaults for copy or download flows.

**Notes**
- This section should focus on defaults that reduce repeated setup, not on
  per-provider configuration.
- Transfer defaults should be phrased in user terms, for example whether files
  download to a default location or prompt each time.
